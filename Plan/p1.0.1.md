## 4.2 JSON Lines protocol

Use one JSON object per line.

Every protocol message must contain:

```
{
  "protocolVersion": "1.0",
  "id": "unique-message-id",
  "type": "request",
  "command": "ping",
  "payload": {},
  "timestamp": "2026-11-12T12:00:00Z"
}
```

Use an ISO 8601 UTC timestamp.

Define and validate message types.

Supported message types:

- `request`
- `response`
- `event`
- `error`

Use unique request IDs to correlate requests and responses.

### Required protocol commands

| Command      | Purpose                                        |
| ------------ | ---------------------------------------------- |
| `hello`      | Worker initialization and capability handshake |
| `ping`       | Heartbeat request                              |
| `shutdown`   | Graceful worker shutdown                       |
| `get_status` | Retrieve worker health and runtime status      |

### Required worker events

| Event                  | Purpose                                  |
| ---------------------- | ---------------------------------------- |
| `worker.ready`         | Worker initialized successfully          |
| `worker.shutting_down` | Shutdown initiated                       |
| `worker.error`         | Unexpected worker error                  |
| `worker.status`        | Periodic or requested health information |

### Protocol rules

- Every line must be independently parseable JSON.
- One malformed request must not crash the worker.
- Invalid messages must return structured errors whenever possible.
- Unknown commands must return a clear error.
- Missing fields must be validated.
- Request IDs must be preserved in responses.
- Never print debug information to stdout.
- Handle EOF correctly.
- Handle large input lines safely.
- Avoid blocking the entire worker while processing a command.
- Do not silently discard failed messages.

Use a clearly documented protocol schema.

# 8. Crash Recovery & Lifecycle

Implement a controlled worker lifecycle.

Required lifecycle:

```
STOPPED
   │
   ▼
STARTING
   │
   ▼
HANDSHAKING
   │
   ▼
HEALTHY
   │
   ├── graceful shutdown ──► STOPPING ──► STOPPED
   │
   └── unexpected failure ─► UNHEALTHY
                                  │
                                  ▼
                              RESTARTING
                                  │
                                  ▼
                               STARTING
```

### Crash recovery requirements

- Detect unexpected process exit.
- Reject all pending requests associated with the terminated process.
- Record the exit code and signal.
- Attempt controlled restart when appropriate.
- Prevent restart loops.
- Use exponential backoff.
- Support a configurable maximum restart count.
- Reset failure counters after a stable healthy period.
- Stop automatic restarts when the application is shutting down.

Suggested defaults:

- Maximum automatic restarts: 3.
- Initial restart delay: 1 second.
- Maximum restart delay: 15 seconds.
- Exponential backoff between attempts.

**Important:** Do not restart a worker indefinitely.

Do not automatically restart a worker after an intentional shutdown.
