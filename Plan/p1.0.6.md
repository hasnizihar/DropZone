# 2. Milestone Objective

Implement two related capabilities.

**A. Playlist downloads**

- Detect supported playlists and multi-item media URLs.
- Inspect playlist metadata.
- Let users choose which entries to download.
- Support selecting all, deselecting all, and selecting individual entries.
- Enqueue selected entries through the existing queue.
- Display aggregate progress and individual item status.

**B. Batch downloads**

- Accept multiple URLs in one operation.
- Analyze and validate each URL independently.
- Support mixed URL types where already supported:
  - Media
  - Direct files
  - Individual images
  - Supported galleries
- Allow users to review and select valid entries before enqueueing.
- Enqueue selected items through the existing queue.

The objective is a reliable multi-item workflow, not a new download engine.

# 3. Architecture Rules

Preserve the existing architecture:

**Electron Main**

- Remains the sole authority for queue state and scheduling.
- Owns batch and playlist parent jobs.
- Coordinates child jobs.
- Enforces concurrency.
- Aggregates progress and lifecycle state.

**Python Worker**

- Performs playlist inspection and metadata extraction.
- Continues using the existing download engines.
- Does not create or manage a separate global queue.

**React Renderer**

- Provides playlist selection and batch review interfaces.
- Submits validated jobs through typed IPC.
- Displays authoritative queue snapshots and events.

**Zustand**

- Remains a projection of Main process state.

Do not create a second scheduler or bypass `QueueManager`.

Do not add SQLite or permanent persistence in this milestone.

# 9. Queue Parent-Child Architecture

Extend the existing parent-child job architecture carefully.

Use parent jobs for:

- Playlist download groups.
- Batch download groups.

Use child jobs for individual downloads.

The parent job must not consume an active download concurrency slot.

Child jobs must use the existing global scheduler.

Requirements:

- A child job must never execute twice.
- Parent cancellation must cascade to active and queued children.
- Parent progress must aggregate meaningful child progress.
- Parent completion must wait for all selected children to reach terminal states.
- Parent failure must accurately represent partial failures.
- A mixture of completed, failed, and cancelled children must be represented clearly.
- Parent retry must not blindly duplicate already completed children.
- Parent state must remain consistent after a worker crash.
- Removing a parent must not orphan active children.

Define and document the behavior of:

- All children completed.
- Some children failed.
- All children cancelled.
- Parent cancelled during active downloads.
- Parent containing no valid selected entries.
- Retry after partial completion.

Choose the safest model for partial retries.

Do not restart successful child downloads simply because another child failed.
