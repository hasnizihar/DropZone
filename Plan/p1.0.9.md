# Milestone 9: QA & Fault-Tolerance Hardening

## 1. Mission

Perform a comprehensive quality assurance, reliability, security, and fault-tolerance hardening pass across DROPZONE.

The goal is to identify and eliminate defects that could cause:

- Application crashes.
- Corrupted or lost downloads.
- Incorrect queue states.
- Broken pause, resume, cancellation, or retry behavior.
- Database corruption or persistence failures.
- Orphaned subprocesses.
- Unsafe file operations.
- UI freezes or unresponsive controls.
- Incorrect recovery after unexpected application termination.
- Packaging or runtime failures on Windows.

This milestone must validate the complete application, not just individual functions.

Do not introduce unnecessary features or redesign the application.

## 4. Queue State Machine Hardening

QueueManager is the authoritative owner of live execution state.

Review every valid and invalid transition.

Test:

- Pending → downloading.
- Downloading → paused.
- Paused → downloading.
- Downloading → completed.
- Downloading → failed.
- Downloading → cancelled.
- Downloading → processing.
- Processing → completed.
- Processing → failed.
- Processing → cancelled.
- Failed → retry.
- Interrupted job → recovery or retry.

Adapt tests to the actual existing state machine.

### Required fault scenarios

- Cancel a job immediately after creation.
- Cancel while waiting in the queue.
- Cancel during active download.
- Cancel during FFmpeg processing.
- Pause while progress events are arriving.
- Resume a partially downloaded HTTP file.
- Retry a failed job.
- Retry a failed post-processing task without downloading again.
- Attempt duplicate cancellation.
- Attempt duplicate retry.
- Receive late progress events after cancellation.
- Receive completion events after a job has already failed.
- Receive malformed or unexpected worker events.
- Shut down while jobs are active.
- Shut down while parent-child jobs are active.

### Scheduler correctness

Verify:

- FIFO scheduling remains correct.
- Maximum concurrency is never exceeded.
- Cancelled jobs release concurrency slots.
- Failed jobs release concurrency slots.
- Completed jobs release concurrency slots.
- Parent containers do not consume child execution slots unless the current architecture explicitly requires it.
- Parent-child aggregation remains accurate.
- One child failure does not incorrectly erase successful child results.
- Removing a parent does not leave orphaned active children.
- Duplicate events do not cause duplicate completion or duplicate history records.

Prevent race conditions and stale asynchronous callbacks from changing terminal job states.

## 5. Network Fault-Tolerance Testing

Build a local HTTP fault-injection test server.

It should support configurable responses and failure conditions.

### Test cases

**Connection failures**

- Connection refused.
- Connection reset.
- Server disconnects during download.
- Connection timeout.
- Delayed response headers.
- Slow response body.

**HTTP responses**

- 200 OK.
- 206 Partial Content.
- 301 and 302 redirects.
- 307 and 308 redirects.
- 403 Forbidden.
- 404 Not Found.
- 416 Range Not Satisfiable.
- 429 Too Many Requests.
- 500 Internal Server Error.
- 502 Bad Gateway.
- 503 Service Unavailable.

**Resume behavior**

- Correct Range support.
- Server ignores Range and returns 200.
- Incorrect Content-Range.
- Changed ETag.
- Changed Last-Modified.
- Resource size changes between attempts.
- Partial file larger than expected.
- Partial file missing its metadata sidecar.
- Invalid or corrupted resume metadata.

Verify that a resume attempt cannot silently append incompatible content to an existing partial file.

Verify that the direct HTTP engine restarts safely when the server does not support the expected range request.

### Redirect and URL security

Test:

- Redirect chains.
- Maximum redirect count.
- HTTPS-to-HTTP downgrade.
- Redirect to localhost.
- Redirect to private IPv4.
- Redirect to private IPv6.
- Link-local addresses.
- Cloud metadata addresses.
- IPv4-mapped IPv6 addresses.
- DNS resolution changes.
- Invalid URL schemes.
- Malformed URLs.
- Redirect loops.

Ensure all redirects are validated, not just the original URL.

Never weaken SSRF protections to make a test pass.

Use temporary directories and controlled filesystem mocks.

Test:

- Destination directory does not exist.
- Destination directory is read-only.
- Disk becomes full during download.
- Disk becomes full during FFmpeg processing.
- Output file already exists.
- Filename collision.
- Invalid filename.
- Windows reserved filename.
- Path traversal attempts.
- Unicode filenames.
- Very long filenames.
- File locked by another process.
- Permission denied during rename.
- Atomic rename failure.
- Partial file cleanup.
- Temporary staging file cleanup.
- Application shutdown during file writing.
- Source file missing before post-processing.
- Output file missing after a persisted completed state.

### Data preservation rules

- Never overwrite an existing user file silently.
- Never delete the original downloaded source before verified output finalization.
- Never mark a file completed before the final output has been verified.
- Preserve recoverable partial downloads when safe.
- Remove temporary files only when they are known to belong to the failed operation.
- Never perform cleanup using an unvalidated arbitrary path.

Test atomic finalization behavior, including failures between temporary-file creation and final rename.

## 7. FFmpeg and Subprocess Reliability

Test FFmpegService under realistic failure conditions.

### Executable failures

- FFmpeg unavailable.
- FFprobe unavailable.
- Invalid executable path.
- Executable exists but cannot be launched.
- Unsupported codec.
- Unsupported output container.
- Invalid media input.

### Runtime failures

- FFmpeg exits with non-zero status.
- FFmpeg hangs.
- FFmpeg produces no output.
- FFmpeg produces malformed output.
- FFprobe verification fails.
- Input contains no audio stream.
- Input contains no video stream.
- Input duration is unavailable.
- Disk becomes full.
- Output file is locked.
- Process is terminated externally.

### Cancellation and shutdown

Verify:

- Cancellation terminates the correct process.
- Child and grandchild processes are cleaned up.
- No FFmpeg processes remain after cancellation.
- No orphaned worker subprocesses remain after application shutdown.
- Graceful termination has a bounded timeout.
- Force termination occurs only when required.
- Temporary outputs are cleaned up safely.
- The original source remains intact.

Test Windows process tree behavior specifically.

Do not assume Unix process signals or process-group behavior applies to Windows.

### Output verification

Verify that a processing job cannot become completed unless:

1. FFmpeg exits successfully.
2. The expected output exists.
3. The output is non-empty.
4. FFprobe validates the output.
5. Required streams exist.
6. The final file is successfully committed.

## 8. SQLite Reliability and Recovery

Use temporary databases for all destructive tests.

Test DatabaseManager and repositories under:

- Missing database.
- Empty database.
- Valid existing database.
- Invalid database file.
- Corrupted database.
- Failed migration.
- Interrupted migration.
- Failed disk write.
- Read-only database directory.
- Database lock contention.
- Application shutdown during persistence.
- WAL checkpoint failure.
- Invalid stored settings.
- Invalid stored job metadata.
- Duplicate job IDs.
- Parent-child foreign key violations.

### Migration tests

Verify:

- Migrations execute sequentially.
- Existing data survives upgrades.
- A failed migration rolls back correctly.
- Schema version does not advance after a failed migration.
- Opening an existing current-version database does not rerun migrations unnecessarily.
- Future schema versions are handled safely.

### Persistence consistency

Verify:

- A job's terminal state is saved.
- Parent-child relationships survive restart.
- Settings survive restart.
- Interrupted jobs are reconciled correctly.
- Completed jobs are not accidentally rescheduled.
- Duplicate lifecycle events do not create inconsistent records.

### Important sql.js consideration

The project uses sql.js with in-memory database operations and disk persistence.

Audit the atomic disk commit implementation carefully.

Verify that:

- The database is not silently left with unsaved changes.
- Disk writes do not overlap unsafely.
- Concurrent persistence requests are serialized.
- A failed disk write is reported.
- Temporary database files are cleaned up safely.
- A valid previous database is not destroyed by a failed replacement.
- The application does not claim data is durable before the disk commit succeeds.

Do not replace sql.js with a native SQLite dependency during this milestone unless a demonstrated reliability defect makes the existing implementation untenable. Any such architectural change requires evidence, a migration plan, and explicit documentation.
