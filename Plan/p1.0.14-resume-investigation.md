## 1. Executive Summary & Problem Statement

During Stage 5.1 manual testing against the OVH speed test endpoint:
- **Test URL:** `https://proof.ovh.net/files/100Mb.dat`
- **Observed Behavior:** Intermittent resume failures occurred when pausing and resuming downloads, resulting in the error:
  `Rate limited by server (HTTP 429)`

The goal of this investigation was to trace the resume flow from the desktop UI through Electron IPC, `QueueManager`, the Python worker, and the HTTP direct stream engine, identify the root causes of the rate limit failures, implement robust HTTP 429 backoff and Range handling, and verify resilience using a controlled deterministic local HTTP server and live transfer tests.

---

## 2. Root Cause Analysis

Tracing the execution flow across the stack revealed two major architectural defects and two secondary resilience gaps:

### 2.1 Redundant HEAD/GET Server Inspection on Every Resume (Primary Driver)
- **File & Function:** `backend/worker/src/dropzone_worker/services/direct_stream_engine.py` $\rightarrow$ `DirectStreamEngine.execute_download()`
- **Mechanism:**
  Whenever a user paused and resumed a download, `QueueManager.resumeJob()` triggered `startDownload()` on the Python worker. Inside `execute_download()`, the engine unconditionally executed:
  ```python
  inspect_res = self.http_service.inspect_url(url, ...)
  ```
  This immediately dispatched a `HEAD` request (or fallback `GET`) to the remote server, even though a valid partial download (`.part`) and sidecar metadata (`.part.meta.json`) already existed on disk with `etag`, `lastModified`, `expectedBytes`, and `finalFilename`.
  Immediately after this inspection, the engine opened a second connection issuing `GET` with `Range: bytes={existing_bytes}-`.
- **Impact on Rate Limiting:**
  Burst testing against `proof.ovh.net` demonstrated that its Nginx front-end enforces a strict rate limit bucket allowing only ~3 rapid requests before issuing `HTTP 429 Too Many Requests` with `Retry-After: 10`.
  Because DropZone sent 2 HTTP requests on initial start (HEAD + GET) and another 2 requests on every resume (HEAD + GET), a single pause/resume cycle generated 4 requests in rapid succession, tripping the server's rate limiter immediately.

### 2.2 Lack of HTTP 429 Backoff & Premature Fatal Termination
- **File & Function:** `direct_stream_engine.py` and `direct_http_service.py`
- **Mechanism:**
  Upon encountering `status_code == 429`, the engine completely ignored the `Retry-After` header. It immediately raised:
  ```python
  WorkerProtocolError(ProtocolErrorCode.RATE_LIMITED, f"Rate limited by server (HTTP 429) for '{current_req_url}'.")
  ```
  This triggered a `download.failed` worker event, which prompted `QueueManager.ts` to permanently transition the job status to `'failed'`, terminating the download and requiring manual user intervention.

### 2.3 Non-Range Server Handling & Overwrite Protection
- If a server responds with `200 OK` rather than `206 Partial Content` (ignoring the `Range` request header or lacking Range support), the engine previously reset `mode = "wb"` and `downloaded_bytes = 0`, but did not validate `Content-Range` offsets or guard against partial byte discrepancies.

### 2.4 Progress Display During Retry
- In `QueueManager.ts` `retryJob()`, `job.progress` and `job.downloadedBytes` were reset to `0` prior to worker engagement, causing the UI progress bar to flicker to 0% even when substantial `.part` data remained intact on disk.

## 4. Architectural & Implementation Changes

### 4.1 Sidecar-Driven Resume (Bypassing Redundant Inspection)
In `DirectStreamEngine.execute_download()`:
1. Before issuing any network requests, the engine inspects the target directory for `.part` and matching `.part.meta.json` sidecar files.
2. If valid metadata is found where `saved_meta["url"] == url`:
   - Remote metadata (`etag`, `lastModified`, `expectedBytes`, `finalUrl`, `supportsResume`) is loaded directly from disk.
   - The redundant `inspect_url()` call is completely **skipped** (0 initial HTTP requests).
3. The engine immediately issues a single streaming `GET` with:
   - `Range: bytes={existing_bytes}-`
   - `If-Range: {etag}` (or `If-Range: {lastModified}`) per RFC 9110 §13.1.2.
   If the resource was unmodified, the server responds with `206 Partial Content`. If the resource changed, the server automatically returns `200 OK` with the new full entity, resolving freshness in a single round-trip.

### 4.2 Robust HTTP 429 Rate Limiting with Bounded Backoff
1. **`parse_retry_after(header_value)`:**
   - Implemented in `direct_http_service.py` compliant with RFC 9110 / RFC 7231.
   - Supports integer seconds (e.g., `Retry-After: 10`) and HTTP-date strings (e.g., `Retry-After: Fri, 13 Nov 2026 12:00:00 GMT`).
2. **Bounded Exponential Backoff Policy:**
   - Maximum 429 retries: 3 attempts.
   - Maximum single wait duration: 15.0 seconds.
   - Default backoff base: 2.0s exponential ($2.0\text{s}, 4.0\text{s}, 8.0\text{s}$) if `Retry-After` is omitted.
   - Responsive wait using `cancel_event.wait(timeout=wait_seconds)` to ensure instantaneous response to user pause or cancel actions during backoff.
3. **Data Preservation on Cooldown:**
   - If retries are exhausted or server demands cooldown $> 15\text{s}$, `.part` and `.part.meta.json` files are strictly preserved on disk.
   - Raises `RATE_LIMITED` error with explicit user feedback: `"Rate limited by server (HTTP 429)... Partial download preserved; please retry after cooldown."`

### 4.3 Range and Content-Range Validation
1. **`parse_content_range(header)`:**
   - Parses `Content-Range: bytes START-END/TOTAL`.
   - On `206 Partial Content`:
     - Verifies `START == existing_bytes`. If matching, opens file in mode `"ab"` (append) and sets `downloaded_bytes = existing_bytes`.
     - If `START == 0`, server responded with full content; cleanly sets mode `"wb"` and `downloaded_bytes = 0`.
     - If `START` mismatches, logs warning and resets to mode `"wb"` to prevent byte duplication or offset corruption.
     - Automatically updates `total_bytes` from `TOTAL`.
2. **Non-Range Fallback (HTTP 200):**
   - If server returns `200 OK`, mode is set to `"wb"` and `downloaded_bytes = 0`. Any existing partial data is cleanly truncated, ensuring zero duplicate bytes.
3. **File Flushing:**
   - Added immediate `part_file.flush()` after writing each chunk to ensure received data is safely committed to disk prior to any network interruption.

### 4.4 QueueManager State Continuity
- In `QueueManager.retryJob()`, existing `downloadedBytes` and `progress` are preserved on pending retries so UI indicators do not flash to 0% while re-establishing connections.

Tested across 7 deterministic local scenarios:

| **2** | **HTTP 429 with `Retry-After`** | Server returns 429 $\times 2$ with `Retry-After: 1`, then 200 | **PASSED** | Waited 4.14s total across 3 attempts, SHA-256 match |

| **4** | **Permanent 429 Budget Exhaustion** | Server returns 429 with `Retry-After: 60` ($> 15\text{s}$) | **PASSED** | Raised `RATE_LIMITED`, `.part` file (20KB) & `.meta` preserved |
| **5** | **Non-Range Server Overwrite** | Server ignores Range and returns 200 with full content | **PASSED** | Overwrote 50KB junk cleanly, exact 262KB, zero corruption |

| **7** | **Repeated Pause/Resume Cycles** | Consecutive pause $\rightarrow$ resume $\rightarrow$ pause $\rightarrow$ resume cycles | **PASSED** | Cycle 1: 65KB, Cycle 2: 131KB, Final: 262KB, SHA match |

## 6. Remaining Limitations & Constraints

1. **Extreme Cooldown Thresholds:**
   If a remote server enforces an extraordinary rate limit wait time ($> 15\text{s}$, e.g. 1 hour or 1 day), the worker will not block indefinitely in a sleep loop. Instead, it preserves partial data on disk and flags the job with a `RATE_LIMITED` status code so the user can resume manually when the cooldown expires.
2. **Dynamic Range Shifting:**
   If a CDN changes content dynamically without updating `ETag` or `Last-Modified`, the server may return `200 OK` rather than `206 Partial Content`. In this case, DropZone safely overwrites from byte 0 to guarantee data integrity rather than risking a corrupted binary.
